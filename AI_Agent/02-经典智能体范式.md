## 学习目标

把 ReAct、Plan-and-Solve、Reflection 放在同一控制框架中比较，能说明每种机制改变的是哪一段流程，以及它新增的失败模式。

## ReAct：用观察修正下一步行动

ReAct 把推理与环境交互连接起来。一次行动取得观察，观察又改变后续决策。外部检索、计算等操作使系统能够获取提示词里原本没有的信息。

```text
用户：计算两份材料的总学习时长
动作：调用检索，找到时长字段
观察：材料 A 为 18 分钟，材料 B 为 24 分钟
动作：调用 add(a=18, b=24)
观察：42
结束：合计 42 分钟，并指出材料来源
```

本仓库记录动作、参数、观察和终止状态，用于复盘可见行为。执行器不需要访问模型的内部思考过程。

核心循环见[core.py](examples/core.py)：

```python
from core import ScriptedModel, Tool, ToolRegistry, final_action, run_agent, tool_action

tools = ToolRegistry()
tools.register(Tool("add", "求和", {"a": "number", "b": "number"}, lambda a, b: a + b))
model = ScriptedModel([tool_action("add", a=18, b=24), final_action("42")])
result = run_agent(model, tools, "计算 18 + 24", max_turns=4)
print(result.status, result.answer)
```

该片段在 `AI_Agent/examples` 目录中运行。`ScriptedModel` 的结果事先给定，适合验证控制流程；真实模型调用方式见[示例目录](examples/README.md)。

### 容易出现的错误

- 工具返回“超时”，模型却将其理解为“查询对象不存在”。应区分操作失败与事实判断。
- 多次执行相同动作而状态没有进展。设置模型轮数预算，并记录重复动作。
- 模型声称完成，实际未取得必要证据。需要独立的任务验收规则。

## Plan-and-Solve：先拆分再求解

原始 Plan-and-Solve 提示强调先制定计划，再解决问题。工程系统可以把计划进一步外化成结构化步骤、依赖和产物，便于校验与重试。

| 阶段 | 输入 | 输出 | 必须校验的条件 |
| --- | --- | --- | --- |
| 规划 | 目标、约束、工具能力 | 步骤列表与依赖 | 数量有界、ID 唯一、依赖有效 |
| 执行 | 当前步骤、已完成依赖 | 结构化结果 | 使用了正确输入、结果满足步骤要求 |
| 重规划 | 失败原因、剩余目标 | 更新后的后续计划 | 保留已验证结果，避免重复副作用 |

[patterns.py](examples/patterns.py) 的 `plan_and_solve` 在执行前校验整个计划，按顺序把依赖结果传给执行器。本例只接受“依赖前面步骤”的有向无环计划，执行失败直接抛出，不包含自动重规划。

### 计划何时需要改变

遇到检索为空、资源不可用、用户约束变化时，原计划可能失效。保留“待执行、执行中、完成、失败”的状态，并为重新规划设置预算。计划文本越长，不代表计划越可执行。

## Reflection：让反馈驱动修改

Reflection 流程可以写成“初稿 → 审查 → 带反馈修改 → 再审查”。审查标准应来自任务要求、测试、规则或证据；只让同一个模型说“看起来不错”容易重复原有错误。

[patterns.py](examples/patterns.py) 的 `reflect` 注入两个函数：`reviewer` 返回是否通过与具体反馈，`reviser` 根据反馈修改。达到修改上限仍不通过时，`accepted=False`，不会把最后一稿自动标成成功。

### Reflection 与 Reflexion

Reflection 是通用反思改进机制。[Reflexion 论文](https://arxiv.org/abs/2303.11366)把反馈写成可供后续尝试使用的语言记忆。二者都可能在推理时运行；除非另做参数更新，否则不会因反思本身改变模型权重。

## 三种范式如何组合

| 范式 | 主要解决的问题 | 适合的情形 | 额外代价 |
| --- | --- | --- | --- |
| ReAct | 下一步需要依据新观察决定 | 信息逐步显露、需使用工具 | 轮数不可预先确定，可能循环 |
| Plan-and-Solve | 多步骤依赖容易遗漏 | 目标可拆分、步骤产物明确 | 计划可能过时，需要重规划 |
| Reflection | 首次输出需要检查和改进 | 有测试、格式或证据检查标准 | 审查也会出错，额外调用增加 |

一个研究助手可先生成子问题计划，每个子问题通过 ReAct 取得证据，再用 Reflection 检查引用和遗漏。组合前要定义各层停止条件，避免“规划层等待执行层、执行层不断反思”的嵌套无限循环。

## 复习与练习

1. 运行 `python AI_Agent/examples/demo.py patterns`，观察依赖传递和一次修改。
2. 把 reviewer 改为永不通过，确认程序返回未解决状态。
3. 为研究助手设计“最大检索次数”和“资料充分”的两个不同停止条件。

原始方法可阅读 [ReAct](https://arxiv.org/abs/2210.03629) 与 [Plan-and-Solve](https://arxiv.org/abs/2305.04091)。
